## 怎么读这份报告

两条判据并列给出，是为了让**它们的差值**暴露问题：

| | 含义 |
|---|---|
| 产物验证通过 | 把生成的产物真的跑起来、喂输入、比对输出 —— **事实** |
| 模型自述完成 | 模型是否以 `finish` / 正文收尾 —— **自述** |

两者不一致时报告会点名：

- **自述完成但验证失败 = 假完成**。最危险的一类：用户拿到跑不起来的代码还以为好了。
- **自述失败但验证通过 = 悲观失败**。能力被低估，通常是模型不敢收尾。

本次两者一致（均 5/5），没有出现偏差项。

> 本次有 3 个任务以 `model_final` 收尾（模型给出正文总结而未调用 `finish`）。
> 它们的正文是真实的完成汇报，产物也确实跑通了，因此判定成立；
> 但 `model_final` 的置信度**低于** `finish`（后者显式声明完成且通过了假完成拦截），
> 所以报告里分开列出而不合并计数。

## 局限（如实写）

- **样本只有 10 个**，且难度梯度不够（10/10 全对 = 区分不出强弱）。
  结论只能说明"在这些任务上"，不能外推成通用能力。
- **"工具失败率"口径有误**：会把"命令按预期以非 0 退出"记成失败，
  而那往往是一次成功的边界验证。待修，见账本 V11 遗留问题。
- **只验证行为，不验证质量**。命名、结构、是否有多余注释都不在评分内。
- **不检查过程是否合理**。靠碰运气跑通的任务同样得满分。
- 任务只用标准库，未覆盖第三方依赖、跨语言等场景；
  也**不含"读几千行代码后改一处"这类长上下文改造**，而那才是真实工程的大头。
