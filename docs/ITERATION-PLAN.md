# MiniCode 夜间迭代账本

> 本文件是**迭代进度账本**，也是开发过程的记录。每个版本完成后状态改为「已完成」并附上实测结论。
> 定时任务每轮读取本文件，挑第一个「待做」的版本开工，做完后回来更新状态。

## 使用方式

每个版本必须走完这条闭环，缺一步都不算完成：

1. 读本文件，找到第一个状态为「待做」的版本
2. 实现该版本列出的改动
3. `python tests/test_smoke.py` 全部通过
4. 实跑一次真实任务验证（不是只看单测）
5. `git add` + `git commit`（一个版本一个提交，提交信息写清为什么这么做）
6. 回来把状态改成「已完成」，填实测结论与遗留问题
7. 继续下一个「待做」版本

## 硬性约束（每一轮都必须遵守）

- **绝不提交密钥**：`api_keys.yaml`、`config.yaml`、`start.py`、`.workbuddy/` 都在 .gitignore 里，
  提交前用 `git status --short` 确认它们没出现
- **不要 push**：仓库还没建远程，本地提交即可
- **不要改已推送的历史**：目前也没推送过
- 每个版本都要能独立工作 —— 时间不够就停在已完成的版本上，不留半成品
- 每轮结束前跑一次完整测试

## V0 edit_block 精确编辑 ✅

**commit**：`5121f47`

**动机**：`write_file` 是整体覆盖语义，改 473 行 HTML 里的一处也得把整个文件重写一遍。
2026-08-29 22:42 那次 `HTTP 400` 就是这么来的 —— 模型输出超长 HTML，参数被截断，连
`path` 都丢了。

**改动**：新增 `edit_block(path, old_text, new_text[, expected_replacements])`
（`agent/tools/filesystem.py`）
- `old_text` 必须唯一才替换；不唯一时返回每一处的行号，让模型补上下文后重试
- 容错：模型常把 `read_file` 的行号（`"   12| ..."`）一起抄进 `old_text`，自动剥离后再匹配
- 找不到时给出排查方向 + 文件中最相近的几行
- 替换前同样走 `.agent_backups` 备份

**实测**：改 473 行 HTML 的标题 → 3 步 / 4.3s，只改一行，文件行数不变。
**测试**：5 个新用例，共 18 个全通过。

**答辩要点**：为什么不直接让 write_file 支持局部改？因为"整体覆盖"的语义必须明确无歧义 ——
一个工具同时有两种写语义，模型更容易搞错。宁可多一个工具，也不要一个工具两副面孔。

## V1 可靠性加固 ✅

**commit**：（见 git log：feat: V1 可靠性加固）

**动机**：录演示视频最怕翻车，而这三类问题在 Windows 上是必现的。

**改动清单**：
1. **中文乱码**（`agent/tools/shell.py`）
   旧实现用 `text=True, encoding="utf-8"` 直接解码，但 Windows 中文环境默认 GBK，
   `dir`/`type`/老工具的中文会成 `������`。
   改为字节流捕获 + 解码顺序：**UTF-8 严格 → 系统 OEM 代码页（cp936/GBK）→ UTF-8 替换兜底**。
   关键修正：不能只用 `locale.getpreferredencoding()`——开启 UTF-8 beta 的机器上它返回 utf-8，
   此时子进程若吐 GBK 字节仍会乱码，必须用 OEM 代码页（`ctypes.windll.kernel32.GetOEMCP()`）。
2. **交互式命令挂死**（`agent/tools/shell.py`）
   旧实现用 `BufferedReader.read(4096)`，它会**一直阻塞到凑满 4096 字节或 EOF**，
   导致进程还活着时读不到已产生的部分输出，交互式检测因此永远不触发。
   改用 `os.read(fd, 4096)`（返回当前可用字节），并增加检测：命令长时间（默认 20s）
   零新输出、且缓冲区停在未换行的提示符上 → 判定疑似等待输入 → 提前终止并给明确错误。
3. **"假完成"拦截**（`agent/loop.py` 的 `_execute_calls`）
   模型改过文件（`write`/`edit` 类变更）却没跑过任何 `run_command` 就调 `finish` 时，
   回灌提示逼它先验证（最多拦 2 次防死循环），跑过命令后才允许收尾。

**实测**：
- 真实任务「写脚本打印中文问候并运行」→ 输出 `你好，世界！` 无乱码；3 步 5.9s 完成。
- 单测 `test_run_command_decodes_chinese_without_garbage`：GBK 文件经 `type` 输出解码正确，无替换字符。
- 单测 `test_interactive_command_is_killed_early`：打印未换行提示符后 sleep 的命令被 1.2s 内识别并终止。
- 单测 `test_fake_finish_blocked_until_verified`：写完文件直接 finish 被拦截，跑过命令后才允许收尾。
- 3 个新用例，共 **23** 个全通过。

**答辩要点**：
- 中文乱码根因是「解码编码假设错误」——不能假设子进程都是 UTF-8；OEM 代码页才是 Windows 非 Unicode 程序的真实输出编码。
- 交互式挂死根因是「读取方式假设错误」——`BufferedReader.read(n)` 是「凑满 n 或 EOF」而非「读到即返回」，
  流式输出必须用语义正确的 `os.read`。两个 bug 都说明：和操作系统/标准库打交道时，不能想当然。

## V2 自修复闭环 ✅

**commit**：（见 git log：feat: V2 自修复闭环）

**动机**：从"能写代码"升级到"能交付正确的代码"——这是 coding agent 的核心竞争力，

   run_command 失败时，提取首个 `File "路径", line N` 与末行错误，**直接读出该处附近源码**

**实测**：

- 单测 `test_build_failure_note_reads_offending_lines`：NameError 的 traceback 被解析，
  出错行 `return a / c` 及其上下 3 行源码被附上。
- 单测 `test_rollback_restores_latest_snapshot`：rollback 把"好"快照拷回，覆盖"坏"文件。
- 单测 `test_self_repair_feeds_traceback_context_and_recovers`：MockBackend 跑「写坏→运行失败→

- 4 个新用例，共 **27** 个全通过。

**答辩要点**：
- 回滚能力不是额外设计的，是从"每次生成都归档"这个规范里**自然长出来**的——
  既然保留了每一次的完整快照，"回到上一个已知可用状态"就是免费的。
- 感知与执行分离：`selfrepair` 只做分析（纯函数、可单测），真正的"修"仍交给模型，
  避免把修复逻辑硬编码成脆弱的规则。

## V4 可审阅性 ✅

**commit**：（见 git log：feat: V4 可审阅性）

**动机**：coding agent 最怕"改了一堆自己都没看清"——无论是对模型还是对用户，改动都应是可审阅的。

**改动清单**：
1. **before/after 采集**（`agent/tools/base.py::ToolContext.record_change`）
   扩展签名接受 `before`/`after`/`path`；`write_file`/`edit_block` 在落盘时记录改动前后内容
   （两侧均超 50KB 自动跳过，避免大文件撑爆会话内存）。
2. **unified diff 渲染**（`agent/tools/review.py::build_diff` + `diff` 工具）
   把本次会话的 changes 渲染成标准 unified diff；新建文件（before=None）显示为全量新增，
   超大数据只列摘要。既是用户的 `/diff` 命令，也是模型可调用的 `diff` 工具——finish 前自查改动。
3. **`/diff` 命令**（`agent/cli.py`）+ 帮助菜单补 `/diff` 一行。
4. **单文件级回退**（`agent/tools/repair.py::rollback` 新增 `files` 参数）
   从「第 N 次」快照里只恢复指定文件（如 `rollback(files=["calc.py"])`），而非整目录回滚；
   做了路径越界校验，杜绝 `../` 逃逸。

**实测**：
- 单测 `test_diff_renders_unified_diff_of_session_changes`：写→改一行→diff，历史里出现 `--- a/` `+++ b/` 与新旧两行。
- 单测 `test_single_file_rollback_restores_only_named_file`：两文件改坏后只回滚 good.py，bad.py 保持坏状态。
- 单测 `test_build_diff_handles_new_and_unchanged`：新建/无变化/超大数据三类边界都正确渲染。
- 3 个新用例，共 **39** 个全通过。

**答辩要点**：
- 可审阅性 = 把"模型改了什么"从黑盒变成可读的 diff；这既是安全网（防意外提交），
  也是自纠错信号（模型能在 finish 前发现"我其实改错了"）。
- 单文件回退比整目录回滚更细粒度，代价只是快照里多一次"挑文件"拷贝——能力从既有归档自然长出。

### 补充修复（commit `e4ba793`，实跑后回补）

首版提交后**实跑真实任务**才暴露的两个缺陷——单测全绿但演示会翻车，
说明"实跑验证"这一步不能省：

1. **所有新建文件的 diff 全部丢失**（最严重）
   `record_change` 用 `before is not None and after is not None` 反推"能否生成 diff"。
   但新建文件的 `before` 本来就该是 None（文件原本不存在），于是被判成"内容过大未采集"。
   实测：一个 32 字符的新建文件，`/diff` 只回一句「改动过大，未生成 diff」——
   而新建恰恰是最该被审阅的一类改动。
2. **`run_command`/`rollback` 被当成文件改动渲染**
   这些是操作、不是文件内容，没有 before/after，却在 diff 正文里刷「改动过大」噪声。

**根因**：`None` 有两种完全不同的含义——"文件原本不存在" vs "内容没采集"，
代码却用一个 `is not None` 同时判断两件事。
**修法**：显式记录 `captured` 标记把两者分开；只有带 `path` 的文件改动才参与 diff。

顺带加固 `write_file`：覆盖写大文件时不再为生成 diff 而把全文读进内存
（超限则流式统计行数、diff 显式标记未采集）。否则 `before=""` 会被解读成
"文件原本是空的"，把一次**修改**显示成**全量新增**——比不显示更糟。

**回归测试**（3 个新用例，共 **43** 个全通过）：
`test_new_file_change_is_diffable_not_mistaken_for_too_big` /
`test_record_change_marks_command_and_oversize_as_not_captured` /
`test_write_over_huge_file_marks_change_not_captured`

**实跑验证**：真实任务「写 greet.py → 改成 Hello, MiniCode → 运行验证」，
`/diff` 正确输出两段 unified diff，命令类操作不再出现；
把 greet.py 改坏后用 `rollback(files=["greet.py"])` 精确还原，同级文件不受影响。

**遗留问题**：diff 是"改后回顾"而非"改前预览"——真要做改前预览得让
`write_file`/`edit_block` 先 dry-run，会多一轮交互，收益不大，暂不做。

## V7 长程记忆：常驻事实层 ✅

**commit**：`cc73b7e`

**动机**：V3 的自动压缩解决了"超窗"，但没解决"遗忘"。原来的 `compact()` 把整段历史
（**包括上一次生成的摘要**）一视同仁地再摘要一次——于是每压一轮，早期信息就被再压
一轮。摘要的摘要会持续衰减，几轮之后"用户要求用 Python 3.11""绝对不要修改
config.yaml"这类硬约束就悄悄消失了，而这恰恰是最不能丢的信息。

**改动清单**：
1. **事实与过程分层**（`agent/history.py`）
   - `History.facts`：常驻事实清单，作为独立消息固定在 index 1；
     `compact()` 用 `protected` 偏移把它排除在被摘要的中间段之外。
   - 摘要提示词要求模型分两节输出：`【关键事实】` / `【过程摘要】`，解析后分存。
   - 事实是**整体重写**而非追加：把旧清单一起喂给模型，要它输出"更新后仍然成立的
     完整清单"。追加式会让事实块单调膨胀，且被推翻的旧结论（"方案 B 已失败" →
     后来其实可行）永远删不掉，反而持续误导后续决策。
   - 模型没按格式分节时**保留旧事实**：宁可这次没更新，也不能因为一次格式不合规
     就让已确认的约束凭空消失。
2. **压缩后重建"可重建的事实"**（`agent/profile.py` + `agent/loop.py`）
   - 压缩后回灌工作区真实文件清单（路径 + 行数，**不含内容**），并明确要求
     "别凭记忆写 old_text"。摘要只答"做过什么"，答不了"磁盘上现在是什么样"；
     不补这一段，模型会拿压缩前的旧记忆去 `edit_block`，`old_text` 必然对不上。
   - 清单只留最新一份（`History.drop_notes`）——它是可重建的事实，价值只在于最新。
   - 自动压缩与手动 `/compact` 统一走 `AgentLoop.compact_context()`，两条路径行为
     必须一致，否则本身就是 bug 温床。

**实测**（真实端点 NSCC MaaS / Qwen3.5，把 `max_context_tokens` 临时调到 20000、
`compact_threshold` 调到 0.3 以强制触发压缩）：
- 压缩触发 2 次，任务 6 步 / 6 次工具调用 / 0 失败 / `finish` 结束。
- 模型产出的事实块如实保住了硬约束：
  「测试必须使用 python 原生 assert，**禁止使用 pytest**」。
- 会话日志里事实块与工作区清单各恰好 1 份，无重复堆积。
- **测试 68 → 77**（新增 7 条 + 订正 1 条断言）。

**实跑才暴露并修掉的两个缺陷**（单测全绿时都没发现）：
1. **摘要压缩有"最小体积"，压完反而更大**
   system 提示词 + 事实 + 摘要 + 最近 N 条是压不掉的底座。预算小于它时，
   实测 5073 → **5178**（不降反升），于是**下一步又压一次**，每步多花一次模型
   调用却什么都没省下。
   修法：追加硬压缩降级（`llm=None`，直接丢弃更早历史且**不调模型**，便宜且有效），
   降级次数上限 4 次，保留下限设为配置值的一半——实测降到 2 时模型会彻底失去线索，
   转头去重新 `read_file` 找状态，省下的 token 又用更多轮次花出去了。
   压到下限仍超预算时，如实提示该调哪个旋钮（`max_context_tokens` / `compact_threshold`），
   而不是继续闷头压。
2. **连续压缩堆出多份已过期的工作区清单**，白占上下文。

**答辩要点**：
- 长程记忆的关键不是"存得下"，而是**区分过程与事实**：过程可以摘要、可以丢；
  事实（用户约束、技术选型、已失败的方案）必须常驻，且只能追加/修订，不参与摘要。
  这一刀切下去，信息衰减就被截断在过程层。
- 事实块**整体重写而非追加**：被推翻的结论必须能消失，否则一份"永远只增不减"的
  事实清单会自己变成噪声源。
- 类比：这就是 agent 的"工作记忆 vs 长期记忆"——摘要是易失的，事实是持久的。

**遗留问题**：
- 事实块的正确性完全依赖摘要模型。它若漏写或写错一条，我们无法检测。
  可以做"事实溯源"（每条带来源消息 id），但收益不确定，暂不做。
- 事实块目前只在本会话内持久；退出 REPL 即失（跨会话恢复仍未做，见末节）。

## 本轮被**否决**的方案：工具结果缓存（附否决依据）

曾计划给 `read_file` 加内容指纹缓存（mtime_ns + size 校验失效）。**做完设计后否决**，
理由记录在案，避免以后重复讨论：

- **它优化的是错误的 5%**。本仓库自己的性能基准（commit `741310d`）实测：
  等模型 94.0%、执行工具 5.2%。即使缓存命中率 100%，也只能省下约 4% 的墙钟时间，
  却要引入一整类"读到脏数据"的风险。**优化应当对准瓶颈（减少轮数与上下文长度），
  而不是对准最便宜的那一段。**
- 顺带得到的判据（可用作通用原则）：**只有当"校验缓存是否失效的成本 ≪ 重新执行的
  成本"时才值得缓存**。`read_file` 满足（O(1) 的 stat vs O(文件大小的读取)），
  但 `list_dir`/`grep_search`/`find_files` 不满足——它们的结果依赖整棵目录树，
  做指纹就得遍历，而遍历**就是**它们的全部工作量。
- 同理，V7 选择做"减少轮数"（防止模型凭记忆编辑失败重来）而不是"让工具跑更快"，
  正是同一条结论的正面应用。

## V8 会话检查点：长任务中断后能续跑 ✅

**commit**：`977ac79`

**动机**：V3 解决了"超窗"，V7 解决了"压缩遗忘"，但**进程一退就全丢**。
一个跑几十步的长任务（或夜里跑到一半被中断/断网）要重跑，代价极高。
V7 的遗留项里明确记着"事实块只在本会话内持久"，本版补上跨会话的那一半。

**改动清单**（新增 `agent/checkpoint.py`）：
1. **检查点保存/恢复**：`save()` / `latest()` / `load()` / `apply()`。
   核心是**区分必须持久化的状态与可重建的状态**：
   - 必须存：history.messages / kinds / facts、task_name、会话统计
     （usage、工具耗时与次数、压缩次数）。统计也要存——否则 `/stats`
     恢复后从零开始，成本对账就断了。
   - 不存（重建）：backend client、registry、**system_prompt**、project_profile。
     它们依赖**当前**的工具清单与工作区，存一份旧的反而会与现状不符。
   - 所以恢复是「**重建骨架 + 回填历史**」，而不是"整个对象反序列化"。
2. **原子写**（临时文件 + `os.replace`）：中断恰恰发生在写到一半的时候，
   留下半截 JSON 会让下次恢复直接崩掉——**坏掉的检查点比没有检查点更糟**。
3. **恢复后如实告知模型**：注入「这是恢复的会话……不代表你刚刚执行过其中的操作」，
   并补一份工作区真实清单（与 V7 压缩后同理：模型手里的历史是旧的，磁盘是新的）。
4. **写在 `run()` 的 finally 里**：Ctrl-C 中断、模型报错、预算耗尽都会走到，
   而**恰恰是这些非正常结束的场景才最需要能续跑**。
5. **接口**：`--resume`（启动时恢复）/ `/checkpoint`（手动保存）/ `/resume`（REPL 内恢复）。

**实测**（真实端点 NSCC MaaS / Qwen3.5）：
- 第一轮：写 `counter.py`（Counter 类含 increment/value）并运行验证 → 3 步 / 0 失败 / 6.4s。
- 第二轮 `--resume` + 追问"加一个 reset 方法并验证" → **落在同一任务目录**（备份记为"第2次"）、
  恢复 7 条历史、正确给已有文件加上 `reset()` 并跑通验证 → 5 步 / 0 失败 / 7.7s。
- 会话日志确认：恢复提示与工作区清单都已注入模型上下文。
- **测试 77 → 83**。

**答辩要点**：
- 状态分类是这一版唯一真正重要的设计：**"发生过什么"要存，"当前是什么样"要重建**。
  后者依赖当前代码与工作区，存旧的就是拿过期信息喂模型。
- 原子写不是洁癖：检查点的价值恰恰在非正常退出时才兑现，而那是文件最可能写坏的时刻。
- 恢复后必须**明确告诉模型它不是"刚做过"**。agent 的上下文是它唯一的现实来源，
  一份看起来像"我刚才做过"的历史，会让它跳过验证步骤——这是安全相关问题，不是措辞问题。

**遗留问题**：
- 检查点目前按任务名单文件存放，只保留最近一次（同名覆盖）。
  要做"历史版本回溯"得加时间戳轮转，当前需求不明确，暂不做。
- 不跨工作区：换 `-w` 就找不到检查点。目前认为这是合理的（换目录等于换项目）。
- 会话里若含敏感内容，检查点会明文落盘。它落在 `.agent_sessions/`（已 gitignore），
  但仍是明文——正式版应按 `security.py` 的脱敏口径处理，记在待办。

**顺带修**：工作区清单原写死"压缩后"，但恢复会话时并不是压缩场景。
同一段提示被两处复用时，写死场景词迟早会说错——改为按 `reason` 参数传入。

## V9 质量指标：让 /stats 回答"做对了没有" ✅

**commit**：`a8d32a8`

**动机**：成本面板只有效率指标（token / 耗时 / 时间去向），缺质量指标。而质量指标是
做任何改进的**前提**——改一句 system prompt、调一次压缩策略，如果没有可比的量化口径，
就分不清是"变好了"还是"这次任务碰巧简单"。它的定位不是多显示几行数字，
而是给后续每次调优提供对照基准。

**改动清单**（新增 `agent/metrics.py`，约 300 行）：
1. `TaskRecord` / `SessionMetrics`：逐任务记录 + 跨任务聚合。
2. 采集点接在主循环的三处：`run()` 开头打点、finally 结算、`run_command` 后记验证成败。
3. 检查点带上指标（**追加字段，故意不提升 CHECKPOINT_VERSION**：老检查点缺键→空列表，
   新检查点被老代码读→多余键被忽略，两个方向都安全，没必要为此作废用户已有的检查点）。
4. `/stats` 面板增加质量段。

**三条口径设计**（这是本版唯一有价值的部分）：
1. **区分"模型自述完成"与"产物真的能跑"**。结局分布如实列出
   finish / model_final / no_progress / …，不把 `model_final`（只吐正文，可能是"我做不了"）
   与 `finish`（显式调用且通过了假完成拦截）混为一谈。
2. **自修复按"回合"计，而非按"失败次数"计**。一次「修复回合」= 一段连续失败 + 紧随的
   一次成功；轮数 = 这段连续失败的长度。失败 3 次才修好和 1 次就修好是两种能力水平，
   只看总数区分不了。末尾仍在失败的记为"未修复"且**不计入平均值**——
   否则未修好的失败会把平均值稀释，反而掩盖问题。
3. **分母为 0 时给 None 而不是 0**。"没有数据"和"数据是 0"在决策上完全不同；
   从未成功修复过的 `avg_repair_rounds` 返回 None，返回 0 会被读成"一次就修好"。

**顺带修掉一个长期假通过的测试（重要）**：
`test_self_repair_feeds_traceback_context_and_recovers` 声称覆盖"运行失败→回灌出错位置→
修好→跑通"，但脚本只定义了函数、从未调用，`python calc.py` 退出码为 0，压根没触发失败；
而断言写成 `"第 4 行" in joined or "calc.py" in joined`，后者在任何回显里都会命中。
**结果是 V2 的招牌能力（自修复闭环）从未被任何测试真正覆盖过。**
改为用 `div(4, 0)` 触发真实的 ZeroDivisionError，断言换成检查自修复提示真正交付的东西：
出错行号 + 附近源码片段。

**实测**：83 → 90 测试；真实端点任务面板正常显示质量段。

**遗留问题**：
- "返工"用同一路径被写入的次数近似，不完美（改 3 次也可能是合理迭代）。

## V10 评测台：判据是产物，不是模型自述 ✅

**commit**：`9b31f69`

**动机**：单测证明"零件没坏"，评测回答的是另一个问题——**这些零件装起来能不能干成活**。
答辩时最有说服力的不是"我有 N 个测试"，而是"我在 5 个标准任务上跑下来，
产物验证通过率 5/5，平均 5.4 步 / 6.7s"。它同时给后续每次调优提供可比基准。

**核心设计：判据是产物，不是自述**
判断任务是否完成有两条路：A 看 `finish_reason`（便宜但不可信）；
B 真把产物跑起来、喂输入、比对输出（贵但是事实）。选 B。
这与项目已有三处机制同一条原则：假完成拦截、自修复回灌、`/diff` 可审阅——
既然对模型的每一句自述都保留，就更没有理由在"这个 agent 行不行"上采信它的自述。

由此得到副产品指标：**自述结局与产物验证的偏差**
- 自述 finish 但验证失败 = **假完成**（用户拿到跑不起来的代码还以为好了，最危险）
- 自述失败但验证通过 = **悲观失败**（能力被低估，通常是模型不敢收尾）

**改动清单**（新增 `agent/eval.py`）：
1. 5 个标准任务，只用标准库，难度有梯度：
   新建 calc（含除 0 边界）/ 修 stats.py 的 bug / 读 scores.csv 出报表 /
   dedup 保序去重 / LRUCache 淘汰。失败在哪一档是有信息量的诊断
   （"只会新建、修不了 bug"是一句有效结论）。
2. 每个任务自带 `verify()`，在**子进程**里跑产物——产物语法错、顶层异常都只判这条失败，
   不会带崩整场评测。子进程环境剥掉 PYTHONPATH，避免宿主注入影响结论。
3. 报告同时给出"产物验证通过率"与"模型自述完成率"，并点名两类偏差。
4. `--task` 过滤、`--json` 落盘（便于两次运行对比）、`--max-steps` 覆盖。
   退出码以**产物验证**为准，不是以自述为准。

**顺带修掉一个真实缺陷：空响应被当成成功收尾（评测台实跑才暴露）**
模型返回完全空的响应（无正文、无工具调用）时，文本通道的"没有调用块 = 已完成"默认
把它判成 `is_final`，主循环因此跳过 `_EMPTY_OUTPUT_HINT` 纠错，直接以 `model_final`
收尾、answer 为"模型未给出总结"。后果：**网关抖一下，任务就被记成成功收尾，
而产物可能根本没生成。**
两处修正：① `parser._parse_text`：该默认仅在**确有正文**时成立——沉默不是结论；
② 主循环：纠错重试耗尽仍为空，单列 `empty_response` 结局且**不计入成功率**
（它既不是"完成"也不是"解析失败"，不单列就总会被归进某一种筐）。
这是"假完成拦截"的另一半：那边拦"改了文件没验证"，这边拦"沉默被当结论"。

**实测**（NSCC MaaS / Qwen3.5 真实端点，各跑一整轮）：

| | 修复前 | 修复后 |
|---|---|---|
| 产物验证通过 | 5/5 | 5/5 |
| 总耗时 | 42.8s | 36.5s |
| 平均步数 / 耗时 | 5.4 / 7.9s | 5.4 / 6.7s |
| 工具失败率 | 7.7%（2/26） | 0.0%（0/26） |
| 平均 token | 35,513 | 34,962 |

**测试 90 → 96**：新增验证器区分度测试——5 条任务的**正确解必须放行、错误解必须拦下**。
这条不能省：一个恒为真的验证器不会报错，只会安静地给出 100% 通过率，
**比没有验证器更危险**。写验证器时就抓到过一次自身错误：
LRU 的断言把 `put(4,4)` 后该淘汰的键写成了 1（实际是 3，因为此前刚 `get(1)`），
会把正确实现判成失败——若不先用参考解自检，这个错误会让 LRU 任务永远 0 分。

**答辩要点**：
- 判据的选择就是设计：**采信自述是便宜的，采信事实是贵的，但只有后者能支撑结论**。
- 评测台的价值在它跑出来的那一次就兑现了：它暴露了"空响应被当成功"这个缺陷，
  而这个缺陷靠读代码和跑单测都发现不了（单测全绿、注释也写得没错，是**语义默认**错了）。
- 判据要先自检：验证器本身写错，比没有验证器更糟（静默给满分）。

**遗留问题（如实写）**：
- 5 个任务样本太小，结论只能说明"在这些任务上"，不能外推成通用能力。
- verify 只验证接口行为，验证不了代码质量（命名、结构、多余注释）。
- 真实端点有随机性（本次两轮结果就有波动），要看趋势应多次运行取分布。
- 评测不检查"过程是否合理"——一个靠碰运气跑通的任务也会得满分。

## V11 评测任务集 5 → 10：每道题考一个此前没考过的维度 ✅

**commit**：`fa45732`

**动机**：V10 的评测台只有 5 个任务。5 个样本小到支撑不了任何结论——
"5/5 通过"在答辩时等价于"我跑了 5 道题"。V10 的遗留问题里第一条就是这条。

**为什么不是"多出几道同类型题"**：扩样本最省事的做法是复制现有任务换个名字，
但那只是把通过率的分母灌大、让数字变好看，信息量一点没增加。所以本版定了一条
硬约束：**新增任务必须测一个此前没测过的维度**，加之前先自问"它比现有的多测了什么"。

**新增的 5 个维度**（括号里是它比原有 5 题多测了什么）：

| 任务 | 维度 | 多测了什么 |
|---|---|---|
| findkw | CLI 契约：参数进 / stdout 出 | 此前全是"导入调函数"或"跑脚本看固定输出"，**没有"输入改变行为"这一类** |
| wordfreq | 非结构化文本 → 结构化统计 | 归一化（大小写 + 标点）与排序，不只看"算没算" |
| flatten | 递归：任意深度嵌套 | 只展平一层的实现在深嵌套用例上才露馅 |
| bank | 跨模块协作 + 状态一致性 | **失败操作的原子性**——多数实现只顾成功路径 |
| parselog | 日志抽取：按级别过滤并保序 | 从半结构化文本抽信息 + 排除不该进来的行 |

`bank` 这题值得单说：它真正测的是"失败的转账不能留下改过的余额"。
多数实现会先把源账户扣成负数再抛异常；`total()` 在转账前后不变，就是抓它的抓手。

**两条防作弊 / 防退化的设计（本版最值钱的部分）**：

1. **CLI 任务必须用多组参数验证**。只喂一组参数时，一个**不解析 argv、
   直接 `print` 期望文本**的硬编码脚本也能通过——而 CLI 契约的本质恰恰是
   "输入变，输出跟着变"。换几组参数是最便宜的防硬编码手段。
   已由 `test_cli_verifier_rejects_hardcoded_output` 钉死。
2. **每个任务都必须同时备好"正确解"和"错误解"两份参考实现**。
   原来两条区分度测试是 `for name in _CORRECT_SOLUTIONS` 遍历字典的：
   新增任务时若忘了配参考解，**循环只是少转一圈，测试照样全绿**，
   而新任务的验证器可能压根没被检验过。
   → 新增 `test_every_task_has_both_reference_solutions` 显式比对集合相等。
   这类"什么都不测却报通过"的缺口是本项目反复踩到的坑
   （自修复闭环的假通过断言、`before is None` 的二义性），**凡是靠遍历字典
   驱动的测试，都要配一条"集合相等"的守护**。

**顺带修：报告表格按显示宽度对齐**。`f'{s:<26}'` 按字符数补齐，而 CJK 在终端
占两列，含中文的那一列会整体错位、后面的数字全糊在一起。报告是要贴进答辩材料的，
表格读不了，数字就等于没有。改用 East Asian Width（W/F 记 2 列）计算并手工补空格。

**实测**（NSCC MaaS / Qwen3.5，10 个任务整轮，79.1s）：

```
产物验证通过：10/10   模型自述完成：10/10
平均步数 5.2    平均工具调用 5.3    平均耗时 7.5s    平均 token 34,587
工具失败率 1.9%（1/53）
```

**测试 96 → 100**。

**遗留问题（如实写）**：
- **10/10 反而说明这套题偏简单**。全对意味着它没有区分度：一个更强的模型和一个
  更弱的模型可能都是 10/10。下一步应该是**把难度梯度拉起来**（加长上下文改造类
  任务），而不是继续加同难度任务。
- **"工具失败率"会误记"故意触发异常做验证"**。唯一的 1 次失败出在 `calc`——
  而它的 prompt 恰恰明确要求"验证除 0 抛异常"。若自测脚本让异常直接冒泡，
  退出码非 0 就被记成工具失败，而那其实是**一次成功的验证**。
  口径待改：需要区分"工具调用报错"（真失败）与"命令按预期以非 0 退出"（成功）。
  暂未改，因为要动 `record_verify` 的语义，牵涉 V9 的指标口径，需要单独一轮。
- 仍然是"从零写小模块"，**不含真实工程里的长上下文改造**（读几千行代码后改一处）。
  这类能力目前只能靠长任务实测佐证，评测台覆盖不到。

**答辩要点**：
- 评测集的**结构**比**规模**重要：10 个维度 > 10 道同类型题。前者失败在哪一档
  是有效诊断（"只会新建、修不了 bug"），后者只给出一个好看的百分比。
- 验证器要防两类敌人：**被测对象作弊**（硬编码输出）和**测试自己静默跳过**
  （遍历字典时缺项）。后者更隐蔽，因为它不会报错。

## 下一轮建议（2026-08-30 06:55 更新，按优先级）

1. **修"工具失败率"的口径**（V11 遗留问题，优先级最高）
   现在把"命令按预期以非 0 退出"也记成工具失败——而 `calc` 任务里那恰恰是
   **一次成功的边界验证**。指标口径错了，后面的调优全都建立在错误的读数上，
   这比指标缺失更糟。动手前先想清：怎么区分"工具调用本身报错"（参数错、
   文件不存在）与"命令跑了、按预期返回非 0"（pytest 失败、assert 触发）？
   可能需要在 `run_command` 的回执里带一个显式标记，而不是靠退出码猜。

2. **把评测的区分度做出来**（而不是继续加任务）
   10/10 全对 = 这套题区分不了强弱模型。下一步应该是拉难度梯度：
   加"长上下文改造"类任务（给一份 300+ 行的代码，要求改一处并保证不破坏其它），
   或加多步依赖任务。**先想清**：这类任务的 verify 怎么写才既能自动判定、
   又不会变成主观评分。

3. **多次运行取分布**（`--repeat N`）
   单次结果会波动（本轮与 V10 的两轮对比就能看出）。加 `--repeat N` 输出
   中位数与方差，把"一次跑通"升级成"稳定跑通"。这条实现成本低，
   但要注意：N 轮 × 10 任务对真实端点的 token 消耗不小。

## 环境坑补充（本轮新踩）

- **`env -u PYTHONPATH` 会让受管 venv 的 Python 完全不输出 stdout**（实测
  `python -c "print('hi')"` 输出为空、退出码 0，极难排查）。
  那条经验原本是针对 **pip/构建** 场景的（避开 shim 的 safe-delete 拦截）；
  **跑本项目自己的脚本时不要加**，直接调用受管 Python 即可。
- 表格对齐：Python 的 `f'{s:<n}'` 按**字符数**补齐，中文报告要按
  **East Asian Width** 算显示宽度（W/F 记 2 列），否则整列错位。

## V28–V31 贴近商业 code agent 的四连击（2026-08-31 夜间，用户授权持续迭代）

在「零框架、自实现核心」已达标的基础上，按「最像商业 code agent 的差距」逐版本补齐：

  门控 8 个写/破坏性工具；`ask` 无交互环境退化为自动放行，拒绝不计入连续失败。提交见 git log。
- **V29 子任务编排**（`agent/tools/agent.py`）：`delegate` 派发受控子智能体，拆大任务为可验证小块、
  降父上下文压力；机制上禁递归（剔 delegate）、不能反问（剔 ask_user）、独立步数预算、失败不拖垮父任务。
- **V30 后台命令**（`agent/tools/shell.py`）：`run_command` 传 `background=true` 立即返回 `job_id`，
  `check_command` 读实时输出、`kill_command` 终止，可后台起服务/跑长任务。
- **V31 自我改进钩子**（`agent/self_improve.py` + `agent/tools/self_improve.py` + `agent/loop.py`）：
  任务结束把本次「失败/修复/中断/压缩」信号沉淀成可泛化经验，落盘 `.minicode/memory.md`
  （与 `memory` 共用同一文件、标 `[auto]`、去重封顶），下次启动自动注入 system 提示词，
  形成「失败→记忆→下次更聪明」闭环（类比 Claude Code / Codex 记忆自更新）。
  纯本地、确定性、不依赖模型，因此完全离线可测；`self_improve` 工具另支持中途 `digest`/`list`/`forget`。

**答辩要点**：这四项是「agent 不只是一个执行器，而是有边界、能分身、能异步、能从错误中学习」的体现；
全部建立在自建的 AgentLoop + ToolRegistry 之上，零框架、零服务端工具，符合考核硬约束。
